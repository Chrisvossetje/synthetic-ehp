# `site/src` — architecture

The web app is organised into three layers. Dependencies only point **down**
(`app → chart/model → types`); nothing in `model/` or `chart/` imports from
`app/`, which keeps the data/maths and the rendering independent of the UI glue.

```
main.ts            Thin bootstrap: load data, build charts, wire controls.

model/             What the data means (no DOM, no rendering).
  settings.ts        viewSettings, Category, selection, shouldIncludeKind.
  dataSource.ts      Load/switch data.ts ⇄ data_stable.ts; getActiveData, find.
  names.ts           Generator-name parsing (generating_name, generates, …).
  tagNames.ts        Curtis → algebraic display names, products, and proof text.
  multiplicationTable.ts  Parse h₀/h₁/h₂ checkpoint tables and look up a sphere.
  multiplicationSource.ts  Lazily load the three root multiplication files.
  multiplicationData.ts    Text imports and parsed tables (loaded on demand).
  spectralSequence.ts  computePage(): the ONE place a page is computed, for all
                       three categories, with the memoised synthetic timeline.

chart/             Generic, reusable rendering (no app/model knowledge).
  chart.ts           Builds the SVG dots/lines and shows/hides them.
  svgChart.ts        The <svg-chart> web component: axes, zoom/pan, grid.
  chartStyles.ts     Per-mode CSS.
  chartMode.ts       EHP vs ASS enum.
  stringMap.ts       Small map keyed by toString().
  infoPanel.ts       The floating info popup.

app/               The actual application: feature controllers + UI wiring.
  charts.ts          The two shared Chart instances.
  ehpChart.ts        EHP chart controller (fill/update/click handlers).
  assChart.ts        ASS chart controller.
  screenshot.ts      Drag-select region → TikZ export.
  truncation.ts      Truncation control ↔ viewSettings translation.
  controls.ts        Every "a control changed → update view" operation, shared
                     by both the DOM listeners and the keyboard shortcuts.
  keyboard.ts        Key → operation table (delegates to controls.ts).

types.ts            Shared data shapes (also imported by generated data files).
data.ts             Generated by logic/ (Rust) — the synthetic EHP dataset.
data_stable.ts      Generated by logic/ (Rust) — the stable AHSS dataset.
tag_translation.ts Generated by export_tag_translation() — algebraic tag names.
```

## Key ideas

- **One page computation.** `model/spectralSequence.ts#computePage(data, query)`
  is the single entry point for "which classes are alive and which
  differentials have fired" on a given page. It dispatches internally between
  the synthetic forward state machine and the algebraic/geometric computation;
  callers pass a `PageQuery` object instead of a long positional argument list.

- **One memoised timeline.** The synthetic category runs the spectral sequence
  forward once into a per-generator timeline and caches it, keyed on *every*
  input that affects the result (truncations, stem window, `applyTauMults`, and
  the fake-data toggle). Reading a page is then a cheap lookup.

- **One copy of each control action.** `app/controls.ts` owns the operations
  (switch mode, set page/category, step truncation, …). The mouse listeners and
  the keyboard shortcuts both call into it, so there is no duplicated logic
  between event handlers.

## Editing the data shapes

`types.ts`, `data.ts` and `data_stable.ts` are part of the generated-data
contract: the Rust exporter in `logic/` writes `data*.ts` (and their
`import … from "./types"` line) directly into this folder. Keep these three at
`site/src/` root, or update `logic/src/io/export.rs` to match if you move them.

## Algebraic display names

`logic::routines::export_tag_translation()` writes `tag_translation.ts`. The
current Rust entry point runs this exporter; regenerate from the repository
root with `cargo run --manifest-path logic/Cargo.toml`. It retains the manual
stable basis choices, exports uniquely determined names throughout the model's
range, and leaves ambiguous choices unresolved. The output is sorted and does
not regenerate the spectral-sequence data or logs.

Translations are keyed by the Curtis tag without its final sphere bracket, so
the same family gets the same algebraic name on every sphere. For example,
`2 3 3[1]` displays as `c_0[1]`, and `3 5 3 3[2]` displays as `1<11, 5>[2]`.
The same file exports `STABLE_TAG_TRANSLATIONS` for AHSS: these tags name stable
AEHP elements directly, using the same manual stable assignments. The dataset
switch selects the matching lookup for labels, products, popups and exports.
Unresolved tags use `?_{stem,af}[sphere]`, with the degree of the tag in the
subscript, until the relevant manual stable assignments are supplied.

`model/tagNames.ts` supplies display names in `alg_name` when either dataset
loads. The original `name` and induced representatives remain Curtis identifiers
for page computations, relations, family highlighting, and multiplication-table
lookup. Labels, tooltips, product/proof text, clipboard names, and TikZ exports
use algebraic names. A clicked class's details include its original Curtis tag.
Angle notation is escaped as text in both SVG labels and the info panel; TikZ
exports convert it to `\langle` and `\rangle`.

Run `npm run test:names` for translation, unresolved cases, proof/product text,
popup escaping, both datasets, and invariance of the page computations.

## Multiplication display metadata

The root `h_0mult.txt`, `h_1mult.txt`, and `h_2mult.txt` files are imported
directly by TypeScript using esbuild's `.txt` text loader. They are separate
from the generated spectral-sequence data and are not used by `computePage`.
The display loads the tables at startup and shows clickable h₀/h₁/h₂
overlays in both the EHP and ASS charts. The hidden `m` shortcut cycles through
none → h₀ → h₀+h₁ → h₀+h₁+h₂ → none in EHP, which defaults to h₀. ASS always
displays all three and ignores `m`; switching views retains the EHP choice. The overlays
are available in algebraic and synthetic views;
the ASS chart always uses the synthetic view.

```ts
import { loadMultiplicationTables } from "../model/multiplicationSource";
import { lookupMultiplication } from "../model/multiplicationTable";

const tables = await loadMultiplicationTables();
const result = lookupMultiplication(tables[1], "7", 9);
// { kind: "sum", targets: ["5 3", "7 1"] }
```

Sphere numbers are those in the multiplication file, not the generator's
bracket index. Each checkpoint applies until the next checkpoint; the last
applies through `max_sphere`. Blank results are `zero`, `?` is `unknown`, and
named results are `sum` with all target terms preserved. Missing sources,
spheres before the first checkpoint, and spheres above `max_sphere` return
`undefined` (no data). Both plain tags (`"7"`) and file notation (`"#(7)"`)
are accepted by the lookup.

`model/multiplicationDisplay.ts` maps Curtis tags to visible generators using
their induced names at the selected sphere. The selected sphere is
`truncation + 1`; with no cutoff, both charts use sphere 70, the table limit,
including all later checkpoints. This coverage limit is internal: product popups
report the earliest sphere supporting the product and its current induced
representatives, including endpoint birth bounds. Inherited tail products also
report their earliest supporting checkpoint rather than the coverage limit.
Targets must resolve uniquely, have the expected stem shift, and be visible.
When a full Curtis tag has no table entry, a stable product on a tail is
inherited while keeping the outer indices fixed. For example, the stable
`#(3) -> #(2 1)` product gives `3[2] -> 2 1[2]`. Explicit zero/unknown entries
and uncovered checkpoints are not replaced. Inherited products are identified
in the popup.
The manually added `1[2n+1] -> h_0[2n+1]` diagonal products supplement the
table lookup. They retain separate product metadata, so table products such as
`1[3] -> h_1[2]` remain available alongside them.
For h₀ sums, each accessible term is drawn even when other terms are hidden or
unresolved. Cross-row h₀ lines require both endpoints to survive to E∞;
same-row h₀ lines require only that both dots are visible on the current page.
Rows use EHP degree in EHP mode and displayed Adams filtration in ASS mode.
h₁ and h₂ require two permanent classes even on the same row, and still require
every term to resolve. ASS displays all resolved operators on its actual class
nodes. Solid lines denote
each term; clicking a line displays the full product and sphere. Clicking
a class always lists all known nonzero h₀/h₁/h₂ products, independently of the
line display setting or category. Zero, unknown, and missing products are
omitted; nonzero products with undrawn terms retain their full sum. The overlay
does not infer tau coefficients or products for artificial ASS target nodes.
Source lookup uses the latest applicable `induced_name` checkpoint. Target
lookup accepts both the original and induced representative of each visible
class. For h₀, endpoint survival is checked before deciding whether a match is
ambiguous; when several eligible dots share a name, the unique permanent
representative is preferred. Other ambiguous matches remain undrawn.
The Rust exporter includes computed induced
names so they remain available after regeneration.

Malformed rows, duplicate sources, unordered/duplicate checkpoints, and
checkpoints beyond the stated coverage fail with filename/line diagnostics.
Run `npm run test:multiplications` to test parsing, bounds, sums, and checkpoint
lookup against all three complete files. `npm test` also runs these checks.
